# Peekaboo adapter boundary

The adapter targets the public Peekaboo 4.5.0 CLI contract at [a1d48b28a3717b16fa5940151de01858714411f6](https://github.com/openclaw/Peekaboo/tree/a1d48b28a3717b16fa5940151de01858714411f6). This is a verified contract baseline, not a vendored runtime or automatic compatibility promise for other versions.

`new PeekabooDesktop(run, sessionProbe)` accepts a trusted asynchronous probe returning `{ready: true, session_id: "stable native session generation"}`. The embedding host must establish an active, unlocked, same-user interactive session and change its identity on session replacement. Permissions alone are insufficient; the default probe fails closed. Inject the adapter through the existing trusted DesktopDriverCatalog factory. No tool argument or registry field enables readiness.

Inventory uses `app list --include-hidden --include-background`, then `window list --pid <pid>`. It exposes at most 100 windows from at most 50 applications. Failed or incomplete provider listings and enumeration limits set `truncated`; an incomplete listing cannot prove window absence. Capture requires an exact numeric window ID, a PID and the provider's lossless `process_start_identity_decimal`. Missing process-generation evidence fails closed. Full titles are compared internally even when public titles are shortened.

Capture calls `see --pid <pid> --window-id <id> --mode window --path <owned temporary file> --format png`. Named reusable snapshots, exact-window diagnostics and matching titles are required. Nonempty screenshot paths must equal the requested destination, with matching coordinate-context window identity. The adapter opens only a regular, single-link file without following symlinks, limits reads to 2 MiB, checks the PNG signature and removes its capture directory in `finally`. DesktopCore additionally validates canonical PNG image data. An explicitly empty screenshot retains semantic observation, but omitted or arbitrary paths fail.

Every action rechecks native session, PID, process generation and exact window/full title after asynchronous lookups. The adapter also enforces a 30-second receipt lifetime from before capture, checking expiry after its final awaited validation so lookup delays cannot extend authority. It supplies PID, window ID and the named capture snapshot to Peekaboo; clicks can reference only element IDs exposed by that capture. Any failure after entering the mutation command is `outcome_unknown`; successful dispatch remains unverified. Single-use consumption, expiry, grant revocation and target authorization remain DesktopCore responsibilities.

These checks do not make separate CLI calls atomic. Peekaboo must enforce its capture-owned snapshot/window mutation identity at dispatch; Styx does not claim it can close an OS race between final validation and native input. The adapter does not expose physical coordinates, use app/title aliases, silently switch windows, grant permissions or unlock a session. Unit fixtures validate the pinned public JSON shapes; native acceptance is a separate gate.

Inventory retains at most 100 unique window locators (window ID, PID, full title, process generation and native session generation). An exact observation can use that locator to query only its owning application's current windows, avoiding a repeated scan of unrelated applications. This caches no readiness, snapshot or mutation authority: live application generation, exact-window/title and session checks still run before and after capture, and again before mutation. A changed locator fails closed until explicit rediscovery. Session changes discard all locators; missing or duplicate locators require fresh bounded discovery. Initial inventory remains sequential and may be slow on hosts with many applications.

Typing explicitly supplies `--accept-dispatched`. In the pinned public `TypeCommand.requireAcceptedTyping`, this changes only the post-dispatch acceptance policy from confirmed receiver change to confirmed-or-dispatched for the same delivery mode. It adds no retry, focus change, target fallback or text clearing. Press and click already report their native outcome without this typing-specific flag. The adapter reads the top-level `DesktopActionOutcome.Projection`: only internally consistent background `confirmed_change` or `dispatched_unverified` results are reported as Styx `dispatched_unverified`, always with `verified:false`. Missing/malformed projections, refusals, partial outcomes, indeterminate dispatch, nonzero exits and transport failures remain `outcome_unknown`. Capture receipt consumption is unchanged. Harness diagnostics should retain only sanitized native error codes/outcome categories, never raw result data or error messages that may contain typed text.

Public source evidence at the contract pin: [typing acceptance policy](https://github.com/openclaw/Peekaboo/blob/a1d48b28a3717b16fa5940151de01858714411f6/Apps/CLI/Sources/PeekabooCLI/Commands/Interaction/TypeCommand.swift#L413), [transport projection fields](https://github.com/openclaw/Peekaboo/blob/a1d48b28a3717b16fa5940151de01858714411f6/Core/PeekabooFoundation/Sources/PeekabooFoundation/DesktopActionOutcome%2BProjection.swift#L76), and [canonical state, route and delivery enums](https://github.com/openclaw/Peekaboo/blob/a1d48b28a3717b16fa5940151de01858714411f6/Core/PeekabooFoundation/Sources/PeekabooFoundation/DesktopActionOutcome.swift#L9). The adapter permits the inspected local/bridge routes and background accessibility action/value, process/window events, native-framework or composite mechanisms; unsupported mechanisms are uncertain rather than silently accepted.

## GUI Bridge execution owner

The adapter supplies the current user's `Library/Application Support/Peekaboo/bridge.sock` explicitly to every CLI command. It never opts into caller-local fallback. Pinned CLI 4.5.0 refuses an unavailable explicit socket with `BRIDGE_UNAVAILABLE`; native read-only verification confirmed this behavior. Readiness requires a GUI host identified as `boo.peekaboo.mac`, its PID, lossless process-start identity and code-signature hash, plus Bridge-sourced Screen Recording, Accessibility and Event Synthesizing grants. The Bridge generation participates in the session receipt; restarting the GUI host invalidates prior observations. This is provider identity evidence, not an independent signature-verification or provenance guarantee. Installation verifies the reviewed app/CLI artifacts separately.

The currently observed native pair is CLI 4.5.0 and GUI 4.9.1 (4090199). Do not infer full compatibility from a successful handshake. The CLI's own local permissions can differ from the selected GUI host; granting rights to a terminal or Coder agent is not required by this adapter. Missing GUI startup, Bridge routing, permissions, console session and target-specific refusal are separate diagnostic stages.

Bounded discovery prioritizes the canonical visible-application inventory before filling the existing 50-application budget from the all-application inventory. Both views must agree on PID generation for priority. This prevents background helpers from hiding a normal visible app while retaining truncation and exact capture checks.

The canonical worker now exposes snapshot-bound typing (at most 500 characters, no NUL), one documented keyboard chord (at most 40 characters), and observed-element invocation. Every native mutation shares the deadline/uncertain-dispatch guard. It does not enable foreground flags, targetless input, multi-chord sequences, automatic retries, or local-runtime outcomes.

A structured native `CAPTURE_FAILED` refusal is surfaced as `capture_unavailable`. This code alone does not establish that the GUI is locked or that privacy permission is missing. The worker preserves the bounded code from unsuccessful native JSON responses without exposing their free-form text. A ready session/permission preflight still requires an actual capture and owned-target input acceptance.
